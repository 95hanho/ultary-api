# 로그인·토큰 재발급 코드 점검 (2026-10-21)

후속 반영: 최초 점검 이후 사용자 결정에 따라 서버 장애의 2회 재시도, 로그인 정보/세션 보존, 현재 세션 로그아웃, 발급별 jti를 구현했다. 이어서 v34에서 DB 잠금·제한적 중복 재발급 복구와 BFF의 만료 Access 복구/1회 재시도를 추가했다. 이후 BFF 공유 키와 prod HTTPS 정책으로 서버 신뢰 경계를 보강했다. 현재 정책은 [`auth-session.md`](./auth-session.md)와 [`bff-server-auth.md`](./bff-server-auth.md)를 따른다. 아래는 최초 점검 당시의 발견 사항이다. 제공자 토큰을 BE에서 직접 검증하는 방식은 추가하지 않았다.

범위: ultary-web의 회원/관리자 쿠키·BFF·OAuth·페이지 가드와 ultary-api의 JWT·인증 필터·로그인·재발급·토큰 Mapper. 운영 장애 로그와 실제 브라우저 세션을 사용한 재현은 하지 않았다. 아래는 코드에서 확인한 동작 및 해당 조건에서의 위험이다. 이번 인증 로직 점검에서는 동작을 변경하지 않았으며, 로그인 후 목적지만 메인으로 변경했다.

## 현재 흐름

- 일반 로그인: 브라우저 → Next BFF → Spring 비밀번호 검사 → JWT 발급 및 DB Refresh Token 저장 → BFF HttpOnly 쿠키 설정.
- 소셜 로그인: Next OAuth 시작/콜백 및 제공자 프로필 확인 → Spring 계정 조회/가입 및 JWT 발급 → BFF 쿠키 설정.
- 재발급: Access 쿠키가 없으면 BFF가 Refresh Token을 Spring에 전달. Spring은 DB의 활성 토큰을 조회하고 기존 토큰을 폐기한 뒤 새 토큰을 발급한다.
- Spring은 STATELESS이며, 재시작 자체로 DB 토큰이 사라지는 구조는 아니다. 동일 비밀키·유효한 토큰·정상 DB 연결이 전제다.

## 우선 확인·개선할 사항

### 1. 소셜 로그인 API의 BFF 신뢰 경계 (높음, 외부 접근 조건부)

`SecurityConfig.java:52`에서 `/api/v1/auth/social/login`이 공개되어 있고, `AuthService.java:85`는 요청의 provider/providerUserId를 신뢰하여 JWT를 발급한다. Spring 코드에는 제공자 토큰 검증이나 BFF 전용 요청 인증이 없다. Spring API가 외부에서 접근 가능하면, 제공자 프로필 식별값만으로 로그인할 수 있는 위험이 있다. 실제 네트워크 접근 제한은 이번 점검에서 확인하지 않았다.

권장: BE에서도 OAuth 제공자 증명을 검증하거나, 해당 API를 인증된 BFF 전용 경로로 제한한다. 네트워크 차단만 있다고 가정하지 말고 배포 설정을 확인한다.

### 2. 재시작·서버 오류가 401 인증 실패로 변환됨 (높음)

FE `src/lib/auth/session.ts:83`과 관리자 `admin-session.ts`의 refresh fetch는 연결 실패 시 쿠키를 유지한다. 그러나 `src/app/api/auth/refresh/route.ts:22`, 관리자 refresh route, `src/lib/api/bffRoute.ts:59`, `sessionUnauthorized`는 이 실패도 401로 응답한다. 5xx 응답 역시 REFRESH_UNAUTHORIZED 메시지로 묶인다.

영향: 재시작 중 토큰 갱신이 겹치면 실제 인증이 유효해도 클라이언트가 로그인이 필요한 상황으로 오인할 수 있다. 이 경로만으로 쿠키가 삭제된다고 단정할 수는 없다.

권장: 토큰 부재/실제 거부는 401, 연결 장애·업스트림 5xx·잘못된 응답은 502/503/504 등으로 구분하고 재시도 가능한 상태로 유지한다. refresh fetch 자체에는 명시적인 timeout도 없다.

### 3. 남아 있는 만료 Access Token의 복구 경로 없음 (중간)

FE `src/lib/auth/session.ts:124`, 관리자 세션은 Access 쿠키 값이 있으면 만료 여부와 관계없이 바로 사용한다. 이후 Spring이 TOKEN_EXPIRED로 거절해도 공통 HTTP/BFF에 재발급 후 재시도하는 경로가 없다. 현재 쿠키 수명을 JWT보다 30초 짧게 두어 일반적인 상황은 완화하지만, 요청 지연·예전 쿠키·수동 보관 토큰까지 복구하지는 못한다.

또한 `src/proxy.ts:28`은 쿠키 존재만으로 `/login`을 메인으로 돌려보내므로 유효하지 않은 쿠키가 남으면 로그인 화면 진입도 방해할 수 있다.

권장: 유효 기간 및 Spring TOKEN_EXPIRED를 처리하는 공통 경로를 마련한다. 상태를 바꾸는 요청은 무조건 재시도하지 말고, 인증 단계에서 거절된 경우만 제한적으로 재시도한다.

### 4. Refresh Token 회전의 동시성·응답 유실 (높음)

FE `src/lib/auth/session.ts:38`의 Promise Map은 동일 모듈 인스턴스에서 진행 중인 요청만 합친다. 관리자도 같다. 여러 프로세스·서버 인스턴스·개발 중 모듈 재로딩을 아우르지 못하며, 첫 요청이 끝난 직후 예전 쿠키로 도착한 요청도 다시 BE를 호출한다.

BE `AuthService.java:201–213`, `AdminAuthService.java:62–77`은 유효 토큰 조회와 폐기 사이에 행 잠금이 없고, 조건부 폐기 쿼리의 갱신 건수도 확인하지 않는다. 같은 토큰을 두 요청이 함께 조회하면 둘 다 새 토큰을 발급할 수 있다. 반대로 첫 회전이 완료된 다음 예전 토큰을 받은 요청은 INVALID_TOKEN으로 거절되며 FE가 쿠키를 지울 수 있다.

DB 회전이 커밋된 뒤 응답이 유실되면 브라우저에는 폐기된 예전 토큰만 남을 수 있다. 이는 실제 장애 재현이 아닌 코드 경로에 따른 가능성이다.

권장: DB에서 회전을 직렬화/원자화하고, 중복 요청·재전송 시 동일한 후속 결과를 받는 정책을 설계한다. 단순 지연이나 재시도만 추가하면 해결되지 않는다.

### 5. JWT 발급별 고유 식별자 없음 (중간)

BE `JwtTokenProvider.java:180–196`은 subject/type/owner/iat/exp로 토큰을 만들며 jti나 nonce를 넣지 않는다. 같은 계정·타입에 같은 초 단위 시각과 만료를 사용하면 동일 토큰 문자열이 나올 수 있다. DB는 refresh_token 문자열로 조회하므로 여러 로그인 세션 또는 빠른 회전에서 세션 구분과 폐기 의미가 흐려진다.

권장: 발급별 무작위 jti 및 세션/회전 계열을 식별하고 DB 정책과 함께 검증한다.

### 6. 로그아웃의 서버 폐기 의미 (중간)

FE `src/app/api/auth/logout/route.ts:18`은 Access 쿠키가 있을 때만 BE 로그아웃을 호출한다. Access가 없거나 서버 요청이 실패해도 브라우저 쿠키만 지우고 성공한다. 이 경우 DB Refresh Token은 유효하게 남을 수 있다.

BE `AuthService.java:218`은 해당 계정의 모든 Refresh Token을 폐기한다. 다른 기기도 다음 갱신 때 로그아웃될 수 있다. 한편 Access JWT는 DB 토큰 폐기 여부를 조회하지 않으므로, 탈취된 Access Token까지 즉시 무효화하는 구조는 아니다.

권장: 현재 세션 로그아웃과 모든 기기 로그아웃을 구분하고, Refresh Token만 있어도 해당 세션을 폐기할 수 있는 경로를 마련한다.

### 7. 소셜 계정 연동은 Access 쿠키만 검사 (중간)

FE `src/app/api/auth/social/{google,kakao}/route.ts`와 `callback/route.ts`의 link 흐름은 `getAccessToken()`만 사용한다. Refresh Token이 살아 있어도 Access 쿠키가 없으면 실패하고, OAuth 제공자 화면을 이용하는 동안 Access가 만료되어도 갱신하지 않는다. MyPage의 UNAUTHORIZED 처리는 로그아웃 API까지 호출한다.

권장: 연동 시작/콜백도 공통 세션 해석을 사용하고, 일시적 실패와 실제 인증 만료를 구분한다.

### 8. Refresh 쿠키 수명과 BE 설정이 별도 관리됨 (낮음)

FE `src/lib/auth/cookie-names.ts:20`은 14일 고정이다. BE `JwtProperties`는 설정값을 사용하고 응답에 Refresh 유효 시간을 전달하지 않는다. 기본값은 일치하지만 개발 환경에서 BE refresh 수명을 바꾸면 만료 쿠키가 남거나 쿠키가 먼저 사라질 수 있다.

권장: BE의 실제 만료를 응답에 포함하고 쿠키에 반영한다.

## 이번에 반영한 이동 정책

- 인증이 없어 보호 페이지에서 이동할 때 `/login`만 사용하고 이전 URL을 쿼리로 전달하지 않는다.
- 일반 로그인·구글 로그인·카카오 로그인 성공 시 메인 `/`으로 이동한다.
- 과거 `returnUrl` 쿼리와 OAuth 복귀 쿠키도 로그인 목적지에 사용하지 않는다.
- 공유 피드 로그인 모달과 계정 연동 실패 후 재로그인도 같은 정책이다.
- 로그인과 별개인 SNS 계정 연동 성공 시에는 기존 설정 화면 복귀를 유지한다. 소셜 최초 로그인 닉네임 안내도 유지한다.

## 확인 범위

변경한 FE 파일의 TypeScript 검사와 ESLint가 통과했다. 실제 소스를 메모리에서 로드하고 Next/쿠키/OAuth 외부 의존성을 모의 처리하여 보호 페이지 이동, 일반 로그인, 구글·카카오 로그인, 과거 복귀 쿠키, 계정 연동 복귀, 닉네임 안내 등 이동 분기 13건을 확인했다. 별도로 업스트림 연결 실패를 모의하여 `clearCookies=false`이면서 응답이 401이 되는 동작도 확인했다. 이 검증은 실제 브라우저·OAuth 제공자·Spring 서버와 연결하지 않았다.

인증 취약성/동시성의 실제 공격·부하 테스트, 운영 DB 변경, 실제 계정 로그인은 수행하지 않았다. 이번 변경은 FE 이동 동작과 문서에 한정된다. 인증 개선은 위 우선순위로 별도 적용해야 한다.
