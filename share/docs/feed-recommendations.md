# 추천 게시글과 무한 스크롤 (2026-11-02)

## 후보와 정렬

- 메인 추천 `/api/v1/main/feeds/recommended`: 본인과 내가 팔로우하는 작성자를 제외한다. 나만 팔로우한 상대·맞팔 상대의 판정은 기존 방향별 팔로우 정책을 따른다. 나를 팔로우하기만 하는 사람은 후보가 될 수 있다.
- 검색 전 그리드 `/api/v1/main/search/recommended`: 본인을 제외하며, 내가 팔로우하는 작성자는 후순위다.
- 두 추천 모두 활성 회원·공개 계정·전체공개 게시글·삭제되지 않은 글·활성 미디어만 포함한다. 차단 관계는 양방향 제외한다. 본인 글·팔로우 공개·나만 공개는 추천하지 않는다.
- 최신 작성일·게시글 번호 내림차순을 기본으로 페이지당 작성자 최대 2개를 우선 적용한다. 상품 30% 제한은 제거했다. 메인의 전용 판매자 글은 일반 목록에서 제외하고 광고로 별도 삽입한다. 상세: `feed-advertisements.md`.
- 후보가 부족하면 작성자·상품 비율 제한을 완화해 채운다. 공개 범위·차단·본인 제외·메인 팔로우 제외는 완화하지 않는다. 최근 30일 같은 기간 제한이나 임의 랜덤 정렬은 없다. 관심사·인기도 점수 기반 개인화는 이번 범위가 아니다.

## API와 커서

- BFF는 위 경로의 `/api/v1` 대신 `/api`를 사용하며 사용자 인증을 유지한다.
- 두 추천 API 응답은 기존 배열에서 `{items: FeedResponse[], nextCursor: string|null}`로 변경했다.
- `limit` 기본값은 메인 10, 검색 18, 허용 범위 1~50. 다음 페이지는 응답의 `nextCursor`를 `cursor`에 그대로 전달한다. `nextCursor=null`이면 끝이다.
- 현재 소규모 포트폴리오 데이터에서는 후보 ID 순서를 첫 요청에 스냅샷하고 남은 ID를 URL-safe Base64 JSON 커서로 전달한다. 서버 메모리에 세션 목록을 두지 않는다. 각 요청은 후보 권한을 새로 조회한 뒤 스냅샷 ID와 교차한다. 이후 새로 작성한 글은 해당 스크롤 도중 끼워 넣지 않으며, 중간 삭제·공개 범위 변경·차단된 글은 제거한다. 사용자·화면이 다른 커서, 중복/비정상 ID는 거부한다.
- 커서는 암호화된 데이터나 인증 수단이 아니다. ID를 바꿔도 서버의 공개·차단 검사를 통과해야 한다. 큰 서비스 규모에서는 전체 후보 조회·ID 스냅샷 대신 정렬 키 기반 조회나 영속 추천 세션으로 확장할 필요가 있다.
- 일반 메인 타임라인은 기존 `{items,nextCursorFeedId}` 계약과 `cursorFeedId`를 유지한다.

## 화면

- 메인은 본인·팔로우 타임라인을 10개씩 먼저 모두 읽고 추천 목록으로 이어진다. 추천도 10개씩 추가한다. 초기 추천 10개는 타임라인과 함께 미리 조회하되 타임라인이 끝난 뒤 표시한다.
- 검색 전 그리드는 18개씩 추가한다. 게시글 링크는 `/posts/{id}`이며 뒤로가기 시 펼친 전체 목록·다음 커서·스크롤 위치를 복원한다. 새 검색 방문 기록에서는 이전 스냅샷을 재사용하지 않는다.
- 하단 근처에서 IntersectionObserver로 다음 페이지를 요청한다. 중복 요청을 잠금으로 막고 게시글 ID도 중복 제거한다. 요청 중에는 작은 회전 아이콘, 끝에는 `마지막 게시글입니다.`를 표시한다. 실패는 마지막 안내로 바꾸지 않고 다시 시도 버튼을 표시한다.
- DB 스키마 변경은 없고 FE·BE 동시 반영이 필요하다.

## 검증

- 추천 후보 SQL의 공개 범위·본인·팔로우 방향·차단·활성 미디어와 상품 태그 분류, 작성자·상품 분산·부족 시 완화·커서 순서·중복 방지·권한 재검사를 자동 검사한다. DB 픽스처는 롤백한다.
- API 응답을 가짜 데이터로 대체한 로컬 브라우저에서 검색 18+18+빈 결과·상세 이동/뒤로가기 복원과 메인 타임라인→추천 10+10+빈 결과·마지막 안내를 확인했다. 이 브라우저 검증은 운영 서버의 실제 추천 결과 검증과 구분한다.
